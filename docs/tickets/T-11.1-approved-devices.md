# T-11.1 – Approved devices for kiosk and clock in/out

**Goal:** a device that is not approved sees an "Approval needed" screen instead of the kiosk at `/kiosk` or the Clock In/Out page at `/clock`, taps "Request access" to send a request, and can use the page only after an Admin approves it on a new Devices page.

**Depends on:** T-10, T-10.1, T-10.2

**Current implementation**

- `/kiosk` (`App\Livewire\Attendance\Kiosk`, T-10.1, layout `layouts::kiosk`) has no login; its actions are `verify()`, `clockIn()` and `clockOut()`, and the view embeds `<livewire:attendance.kiosk-duties />`.
- `/clock` (`App\Livewire\Attendance\Clock`, T-10) checks `attendance.clock` in `boot()`; its actions are `clockIn()` and `clockOut()`; errors use `addError('clock', …)` and the `clock-error` callout.
- Photos are switched on and off with `config('attendance.require_photo')` (`config/attendance.php`, `ATTENDANCE_REQUIRE_PHOTO`, false in `phpunit.xml`) read through `App\Support\AttendancePhotos::required()`.
- Menu items, their routes and permission middleware come from `App\Support\Navigation::items()`; permissions are seeded by `RolesAndPermissionsSeeder::ROLE_PERMISSIONS`; `tests/Feature/RolesAndPermissionsTest.php`, `NavigationTest` and `RouteAuthorizationTest` list every permission and menu route.
- `spatie/laravel-activitylog` v5 is installed (`activity_log` table migrated) but not yet written to.
- A web page cannot read a phone's or tablet's hardware ID, and native apps are out of scope (PRD 4), so a device is a browser on that device, remembered with a long-lived cookie. A different browser, a private window or cleared browser data is a new device that must request access again.

**Build**

- Config: `config/attendance.php` gets `'require_approved_device' => (bool) env('ATTENDANCE_REQUIRE_APPROVED_DEVICE', true)`; `phpunit.xml` sets `ATTENDANCE_REQUIRE_APPROVED_DEVICE=false` so existing kiosk and clock tests keep passing. Read it through `DeviceService::required()`.
- Migration (new file) `create_devices_table`: `id`, `token_hash` (string 64, unique: SHA-256 of the cookie token, never the token itself), `code` (string 7, unique, e.g. `K7F-29Q`, uppercase letters and digits without 0/O/1/I), `name` (string 100, nullable), `status` (string 20: `pending` / `approved` / `blocked`, default `pending`), `requested_from` (string 10: `kiosk` or `clock`), `requested_by` (nullable FK users: the signed-in user who asked from `/clock`; null from the kiosk), `requested_at`, `last_seen_at` (datetime), `browser` (string 100), `platform` (string 100), `user_agent` (text), `ip_address` (string 45), `last_user_id` (nullable FK users), `approved_by` (nullable FK users), `approved_at` (nullable datetime), timestamps, soft deletes; index on `status`.
- Model `App\Models\Device` (`SoftDeletes`; constants `STATUS_PENDING`, `STATUS_APPROVED`, `STATUS_BLOCKED`; `STATUSES` with label and badge color: Approved green, Pending amber, Blocked red; `statusLabel()` / `statusColor()` like `Attendance`), factory with `approved()`, `pending()` and `blocked()` states.
- `App\Support\UserAgent::describe(string $userAgent): array{browser: string, platform: string}` — simple, dependency-free parsing ("Edge", "Chrome", "Firefox", "Safari"; "iPad", "iPhone", "Android", "Windows", "macOS"; otherwise "Unknown"). No new Composer package.
- `App\Services\DeviceService`:
  - `find(Request $request): ?Device` — reads the `wrj_device` cookie (Laravel-encrypted, `HttpOnly`, `SameSite=Lax`, 5 years) and returns its device, or null when there is no cookie, the token is unknown, or the device is archived. **Creates nothing.** For a found device it updates `last_seen_at` and `ip_address` at most once every 5 minutes and re-queues the cookie so its 5-year expiry renews on each visit.
  - `state(Request $request): string` — `allowed` (an approved device, or `required()` is false), `new` (no device yet), `pending` or `blocked`.
  - `requestAccess(Request $request, string $from, ?User $requestedBy): Device` — when the browser already has a pending device, returns it (no duplicate); otherwise creates a random 40-character token, stores a new `pending` device with a unique `code`, `requested_from`, `requested_by`, `requested_at`, the browser, platform, user agent and IP, and queues the cookie. At most 5 requests per IP address per hour (`RateLimiter`); over the limit it throws a `ValidationException` "Too many requests from this network. Try again later."
  - `approve(Device $device, string $name, User $admin)`, `block(Device $device, User $admin)`, `rename(Device $device, string $name, User $admin)`, `archive(Device $device, User $admin)` — each writes `activity('devices')->performedOn($device)->causedBy($admin)` with the old and new status (and name).
  - `recordUser(Device $device, User $user)` — sets `last_user_id` after a successful clock in or clock out.
  - `prunePending(): int` — archives `pending` devices not seen for 30 days.
- Approval screen, one Blade component `resources/views/components/device-approval.blade.php` used by both pages (props: `state`, `code`, `requestedAt`), in a centered white card (`rounded-card shadow-card`) with a large icon:
  - **New device** (`state = new`): shield icon, heading "This device needs approval", text "To keep attendance accurate, only devices approved by your admin can use this page. Tap Request access to send a request.", a primary `btn-accent` button **Request access** (`wire:click="requestAccess"`, `data-test="request-access-button"`, shows "Sending…" while loading), and a muted line "Your admin will see this device's browser and type, not your personal data."
  - **Pending** (`state = pending`): clock icon, heading "Request sent", text "Your admin needs to approve this device. Show them this code:", the device code in large monospace letters (`data-test="device-code"`), "Requested :time" (e.g. "Requested Oct 24, 9:05 AM"), and a secondary **Check again** button (`wire:click="$refresh"`, `data-test="check-again-button"`).
  - **Blocked** (`state = blocked`): no-symbol icon in red, heading "This device is blocked", text "Ask your admin if you think this is a mistake.", the device code, and no request button.
- Kiosk (`/kiosk`):
  - When `state` is not `allowed`, `render()` shows only the approval screen inside the kiosk layout (hero band and floating card); the sign-in form, step bar and `<livewire:attendance.kiosk-duties />` are not rendered.
  - New action `requestAccess(DeviceService $devices)` → `requestAccess($request, 'kiosk', null)`, then shows the Pending screen.
  - `verify()`, `clockIn()` and `clockOut()` return 403 when the state is not `allowed`, so a tampered request cannot skip the screen. After a successful clock in or out, `recordUser()`.
- Clock In/Out (`/clock`):
  - The page header stays; when `state` is not `allowed`, the approval screen replaces the Clock In/Out card and the Today panel (no project picker, buttons or camera modals are rendered).
  - New action `requestAccess(DeviceService $devices)` → `requestAccess($request, 'clock', Auth::user())`.
  - `clockIn()` and `clockOut()` re-check the state on the server and, when not `allowed`, add the `clock` error "This device is not approved for clock in/out." and save nothing. After a successful clock in or out, `recordUser()`.
- New permission `devices.manage` for `admin` only, added to `RolesAndPermissionsSeeder::ROLE_PERMISSIONS` (and to `PermissionCatalog` under Admin as "Manage devices" if T-20 is already built); update the tests that list every permission and menu route.
- Devices page `App\Livewire\Devices\Index` (`#[Title('Devices')]`, view `resources/views/livewire/devices/index.blade.php`), menu item in `Navigation::items()`: `['label' => 'Devices', 'url' => 'devices', 'route' => 'devices.index', 'group' => 'Admin', 'icon' => 'device-tablet', 'permissions' => ['devices.manage'], 'component' => Devices\Index::class]`; `boot()` and every action check `devices.manage`.
  - `<x-page-header>` "Devices", "Phones, tablets and computers allowed to use the kiosk and Clock In/Out."
  - Stat cards: Pending requests, Approved, Blocked.
  - Filter toolbar: search by name or code, status select, `<x-filter-chip>`s and "Clear filters".
  - Table in `<x-data-card>`, paginated with rows per page (`WithPerPage`, `<x-table-footer>`): Device (name or "Unnamed device", the code in a mono pill, and a "This device" badge on the Admin's own browser via `find()`), Requested (from Kiosk / Clock In/Out, by whom when known, and when), Browser / OS, Last seen (relative, exact time in the tooltip), Last user (`<x-avatar>` + name), Status (`<x-status-badge>`), and a `flux:dropdown` with Approve (opens a modal asking for a name, e.g. "Site A tablet"), Rename, Block, Archive. Pending requests first, then newest `last_seen_at`. `<x-empty-state>` when empty; stacked cards on phones.
- Pruning: a daily scheduled command `devices:prune-pending` in `routes/console.php` calls `prunePending()`.

**Acceptance criteria**

- [ ] Opening `/kiosk` on a new browser shows "This device needs approval" with a Request access button, and the sign-in form is not shown; no device is saved until the button is tapped.
- [ ] Tapping Request access saves one pending device and shows "Request sent" with its code; tapping again or reloading shows the same code and saves no second device.
- [ ] Opening `/clock` on a new browser shows the same screen in place of the Clock In/Out card; the request records the signed-in user as `requested_by`.
- [ ] After the Admin approves the code on Devices, "Check again" (or a reload) shows the normal kiosk or Clock In/Out page, and clock in/out works.
- [ ] A blocked device shows "This device is blocked" with no Request access button; an archived device shows the Request access screen again.
- [ ] Direct `verify`, `clockIn` or `clockOut` calls from a device that is not approved save nothing.
- [ ] Only Admin sees Devices in the menu; Staff and Worker get 403 on `/devices`.
- [ ] With `ATTENDANCE_REQUIRE_APPROVED_DEVICE=false`, both pages work as before and show no approval screen.

**Tests**

- Unit: `UserAgent::describe()` — an Android Chrome, an iPhone Safari, a Windows Edge and an unknown string give the expected browser and platform.
- Unit: generated device codes match `^[A-HJ-NP-Z2-9]{3}-[A-HJ-NP-Z2-9]{3}$` (no 0, O, 1 or I).
- Feature (`config(['attendance.require_approved_device' => true])`): `GET /kiosk` with no cookie shows "This device needs approval" and `data-test="request-access-button"`, does not show the sign-in form, and creates no device.
- Feature: kiosk `requestAccess()` creates one pending device with `requested_from = kiosk`, queues the `wrj_device` cookie and shows the code and "Request sent"; calling it again with the same cookie creates no second device.
- Feature: `/clock` `requestAccess()` as a worker creates a pending device with `requested_from = clock` and `requested_by` = the worker.
- Feature: the 6th `requestAccess()` from one IP within an hour shows the "Too many requests" error and creates nothing.
- Feature: with an approved device cookie, the kiosk shows the sign-in form and `/clock` shows the Clock In button; a clock in sets `last_user_id`.
- Feature: with a pending device, kiosk `verify()` returns 403 and `/clock` `clockIn()` adds the `clock` error and creates no attendance.
- Feature: a blocked device shows "This device is blocked" and no request button; an archived device shows the Request access screen.
- Feature: approve, rename, block and archive change the device and each writes an `activity_log` row with the Admin as causer.
- Feature (data provider): `/devices` — admin 200, staff 403, worker 403; guest redirected to login.
- Feature: `devices:prune-pending` archives a pending device last seen 31 days ago and keeps one seen 29 days ago and every approved device.

**Verify:** set `ATTENDANCE_REQUIRE_APPROVED_DEVICE=true`; open `/kiosk` on a tablet, tap Request access and note the code; on a computer, log in as Admin → Admin → Devices, approve the code as "Site A tablet"; tap Check again on the tablet and clock in; open `/clock` on a phone, request access, approve it, and clock in; block the phone and confirm it shows "This device is blocked".
